# v0.4 — Pre-milestone spike scope

Status: scoping (pre-spike). Companion to [`2026-05-21-v0.4-live-property-events-design.md`](2026-05-21-v0.4-live-property-events-design.md) — fills in § 3.1 and § 3.2 of that spec. Findings will be a sibling doc + a `docs/sonos-notes.md § Event model` update.

## 1. Why a spike, and why now

The v0.4 spec defers two coupled decisions to a pre-implementation hardware spike:

1. **Event source path** — upstream reactive layer (`sonos-state` / `sonos-stream` / `sonos-event-manager`) vs. raw `callback-server` + own change-detection.
2. **Cold-start pattern** — `.watch()`-as-seed-probe, hybrid fetch+watch (accepting suppression), or watch + bounded-fetch fallback.

Doing this before any v0.4 code lands keeps `StateManager` design from being authored twice — consistent with the project's spike-first preference for de-risking abstractions.

A third item runs in parallel because it doesn't need hardware:

3. **FRB v2 `Stream<T>` sanity pre-check** — verify the FRB stream surface behaves as the v0.4 spec assumes (single multiplexed stream, sensible threading, clean drop semantics) before writing `StateManager`.

## 2. Hardware context

- Windows desktop dev box on the 4-speaker LAN (same hardware used for v0.3 acceptance).
- Speakers: Beam `.103` (HT primary / coordinator), surround RR `.187` (Invisible satellite), Sonos One `.105` "Kitchen", surround LR `.115` (vanished — powered off).
- Production discovery + topology already proven on this LAN; the spike binaries can call `oto_wire::SonosWire::new().discover()` to seed.

Android is **out** of the spike — GENA NOTIFY is unicast TCP and doesn't need `MulticastLock`; that's the v0.4 acceptance gate's job, not the spike's.

## 3. Time-box

Total: **one focused session, ~3–4 hours of hardware time + ~1 hour FRB pre-check (parallel).**

| Block | Duration | Purpose |
|---|---|---|
| Setup + sanity | 30 min | Both spike binaries compile, can discover + reach each speaker |
| Path A run | 60 min | 30 min idle + 30 min active observation |
| Path B run | 60 min | Same |
| Cold-start probes | 30 min | Three patterns × first-event-arrival timing |
| Findings write-up | 30 min | Sibling doc + sonos-notes update |
| FRB pre-check | 60 min | Hello-world `Stream<Tick>` in Rust, watched from Dart |

If a path is obviously broken in the first 15 minutes (compile failure, dep conflict, library doesn't even bind a port), drop it and document the breakage as the result. Don't sink time into making a non-starter work.

## 4. Path A — upstream reactive layer

Adds to the dep graph: `sonos-state`, `sonos-stream`, `sonos-event-manager` (or whatever the umbrella import exposes — to be confirmed against the `sonos-api =0.5.2` family). `callback-server` is transitively pulled.

**Spike binary:** `native/examples/spike-reactive.rs` (new). Scaffolded as part of the spike, not committed to `main` — lives on a `spike/v0.4-events` branch that's discarded after findings land. The spike findings doc is what gets merged.

**Setup:**
1. `oto_wire::SonosWire::new().discover()` → topology.
2. For each speaker in the snapshot, call the SDK's `.watch()` on volume / mute / transport-state / current-track.
3. Drain the resulting reactive stream into stdout with `[timestamp speaker_id property old→new]` tracing.

**Instrumentation:**
- Event arrival count per minute.
- Per-event latency: change in Sonos app (via wall clock from a phone) → event observed in stdout.
- Watch-after-fetch suppression: does it trigger when expected? Capture a positive example if seen.
- Position updates: does the documented "intermittent position" issue surface in a 30 min active run?
- Subscription renewal: instrument the SDK's renewal callback if exposed, otherwise observe via packet timing.
- Drops / dupes / out-of-order: explicit checks at end of run.

## 5. Path B — raw `callback-server` + own change-detection

Adds to the dep graph: `callback-server` directly. No `sonos-state` / `sonos-stream` / `sonos-event-manager`.

**Spike binary:** `native/examples/spike-callback-server.rs` (new, same throwaway branch).

**Setup:**
1. `oto_wire::SonosWire::new().discover()` → topology.
2. For each speaker, issue GENA `SUBSCRIBE` requests to AVTransport + RenderingControl URIs (per `sonos-notes.md` SOAP table). Renewal handled manually with a timer thread or `callback-server`'s built-in.
3. `callback-server` parses NOTIFY bodies; the spike code parses the property XML (LastChange element, etc.) and emits `[timestamp speaker_id property new]` tracing.
4. Maintain a per-speaker property cache; only emit a trace line when the value actually changes.

**Instrumentation:** same metrics as Path A. Additional metric: lines of change-detection code we own (a proxy for the maintenance cost we'd take on if this path wins).

## 6. Cold-start patterns to evaluate

For **whichever path is leading after § 4 / § 5**, run three short cold-start probes:

1. **Watch-as-seed-probe.** Fresh subscribe, no prior fetch. How long until the first event for each property? Worst case: a property never changes during the probe window — is that visible to the caller, or does it look identical to "subscription stuck"?
2. **Hybrid fetch + watch (accepting suppression).** Run `.fetch()` then `.watch()` on the same property. Confirm the first `.watch()` notification is suppressed when the fetched value matches current state. Confirm subsequent changes do fire.
3. **Watch + bounded-fetch fallback.** Subscribe; if no event arrives within T seconds (try 2 s and 5 s), do a one-shot fetch and seed the cache from that. Observe how often the fallback actually fires on a quiet LAN.

Output: a recommendation matrix — which pattern works on the chosen path, and which one we'll implement in v0.4.

## 7. FRB stream pre-check (parallel — no hardware)

Goal: confirm Rust `Stream<T>` round-trips through FRB v2 as the v0.4 spec assumes. **No** Sonos involvement — synthetic ticks only.

**Spike binary:** a temporary FRB function `dev_tick_stream(interval_ms: u32) -> Stream<u64>` in `native/src/api.rs` (later reverted, or kept behind a debug-only feature gate — decide during the pre-check). A throwaway Flutter widget or Dart test subscribes and logs values.

Verify:

- **Threading.** Which thread pumps the stream? Does FRB pull from an isolate's worker pool, or a dedicated thread? Match this against the planned single multiplexed event-pump thread design.
- **Error propagation.** Yield an error from the stream after N items — does Dart see it as `StreamSubscription.onError`, an `AsyncError` in a `StreamProvider`, or silently?
- **Drop / cancel.** When Dart cancels the subscription, does the Rust side observe the cancellation (so the event-pump thread can clean up its subscriptions)? Or does it have to be polled / time out?
- **Multiple consumers.** Can multiple Dart subscribers fan out from one Rust `Stream`, or do we need to split / broadcast on the Dart side? (Relevant for one-shared-FRB-stream-per-process vs. one-stream-per-StreamProvider.)
- **Hot reload.** What happens to an active stream on Flutter hot reload? Reconnect, error, silent drop?

The answers shape `StateManager`'s public surface and how `speakerStateProvider` is implemented.

## 8. Decision criteria

In priority order for this spike:

1. **Correctness.** Does each path deliver events reliably? Drops, dupes, out-of-order, intermittent property updates? Hard fail on a path that drops core events.
2. **Cold-start tractability.** Does at least one of the three patterns (§ 6) produce a sane initial state on this path?
3. **Code surface owned.** Smaller is better. Path A is ~thin wrapper if the SDK works; Path B requires us to own change-detection forever. Path B's surface is acceptable if Path A is broken.
4. **Long-running stability.** No subscription leaks, no drift, renewal works.
5. **Dep weight.** Tiebreaker only.

A path doesn't have to be perfect — it has to be **good enough that the failure modes are documentable as known issues** (cf. v0.4 spec § 9: "intermittent `position` updates" is acceptable as a CHANGELOG known-issue note, not a hard fail).

## 10. After the spike

writing-plans skill produces the v0.4 implementation plan. Inputs to the plan:

- This scope doc (records why decisions were made).
- The findings doc (records what was decided).
- The four design constraints from v0.4 spec § 5 (extensible enum, single FRB stream, per-kind subscribe / unified delivery, lock-granularity audit).

The plan is **not** written before the findings land. Writing a plan that hedges on the spike outcome doubles the work and produces a worse plan.

## 11. Out of scope for the spike

- Topology change events. v0.5.
- Group form/break commands. v0.5.
- Any Android-specific testing. v0.4 acceptance gate.
- Performance tuning beyond "does it stay up." v0.4 dogfooding via `event-tail.rs`.
- StateManager / Riverpod provider design. v0.4 implementation plan, after spike findings.
- `event-tail.rs` itself. v0.4 implementation plan — it's the dogfooding tool, not a spike artifact.

## 12. Exit criteria

The spike is **done** when:

- Both paths have run at least the planned idle + active blocks (or one path was eliminated early per the § 3 fail-fast rule).
- Three cold-start patterns have a recorded result on the leading path.
- FRB pre-check answers all five questions in § 7.
- Findings doc is written and the sonos-notes update is drafted.
- The decision is reviewable (i.e. someone other than the spike runner could read the findings doc and predict the same outcome).
