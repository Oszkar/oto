# v0.6.3 - Responsive layouts (design spec)

Status: design approved 2026-07-08, pending spec review then task plan.
Milestone: v0.6.3, the final phase of the v0.6 UI series.
Branch: `docs/v0.6.3-planning`. Visual reference: the v0.6.3 board artifact (oto-token wireframes + interactive selection demo).

## 1. Goal

oto is phone-shaped at every width: one column, a floating bottom strip, detail views pushed as full-screen routes. v0.6.3 branches wide layouts so a tablet and a Windows desktop stop wasting the extra glass. It is a **pure Flutter UI pass over the existing providers**: no Rust, no FRB surface change, no new capability. This closes the v0.6 UI milestone; v0.7 is the hardening + polish bucket.

## 2. Scope

### In

- Responsive shell: three tiers keyed on width (see §4.1).
- Desktop three-pane: nav rail + room grid + persistent Now Playing pane (§4.2).
- Tablet master-detail: grid + Now Playing detail pane, no rail (§4.3).
- A selection model driving the wide detail pane (§4.4).
- Detail-screen refactor into embeddable `*Body` + phone `*Screen` wrappers (§4.5).
- Settings + Group editor as breakpoint-aware dialog-vs-route (§4.6).
- Windows window-size/position persistence via `window_manager` (§4.7).

### Out (unchanged from the v0.6 milestone rule)

- Any backend / capability work. This holds for the whole v0.6 series.
- Backend-not-supported controls stay unrendered, never faked: shuffle/repeat/seek, queue, EQ/Sound, search. (The retired `hifi-responsive.jsx` prototype's third desktop pane was a Queue and its chrome included search/shuffle/repeat/EQ - none of which are buildable under the backend-true rule; that is largely why it was retired. See §7.)
- Phone (`<840`) layout: untouched.

## 3. Decisions (locked 2026-07-08)

| Area | Decision |
|---|---|
| Desktop composition | **Grid-primary** three-pane (nav rail / grid / Now Playing pane). Chosen over list-master-detail and now-playing-hero to preserve oto's "everything at a glance" grid identity and minimise the reshape of shipped code. |
| Breakpoints | `<840` compact (today, unchanged) / `840-1200` tablet master-detail / `>=1200` desktop three-pane. Reuse the existing `OtoScaffold.wideBreakpoint = 840` seam; add a `desktopBreakpoint = 1200`. |
| Bottom strip | Phone-only. Its function *becomes* the persistent Now Playing pane on wide. |
| Selection | New `selectedSourceProvider` (a nullable group id, `String?` - ids across the state models are plain `String`), defaults to the first active source else empty. Wide = select-in-place; phone = keep the route push. Empty pane = a quiet "pick a room" placeholder. |
| Room detail | Folded away on wide (phone-only). Its parts already live elsewhere on wide: per-room volume on the card, transport in the Now Playing pane, grouping in the group dialog. |
| Now Playing pane | Includes **per-room level sliders** for a group (salvaged from the retired prototype; backend-true, already how the phone group card behaves), not just member chips. |
| Settings / Group editor | Dialogs on wide, pushed routes on phone, via one responsive helper. |
| Cards / Stack | Kept. Cards is the wide default (packs 3-up in the grid pane); Stack renders as a single narrower column. Low stakes; cut if it complicates the grid. |
| Screen refactor | Split each detail screen into `*Body` (chrome-free, embeddable) + `*Screen` (scaffold + back button for phone routes). Mirrors how `OtoScaffold` already isolates a body slot. |
| Window persistence | `window_manager` package (§7 dependency note). |

## 4. Design

### 4.1 Breakpoint ladder

`OtoScaffold` already carries the seam: a `LayoutBuilder` at `wideBreakpoint = 840` that currently no-ops with a `TODO(v0.6.3)`. Extend it:

- `width < 840` -> compact body (today's phone layout). Unchanged.
- `840 <= width < 1200` -> tablet: master-detail (grid + detail pane).
- `width >= 1200` -> desktop: three-pane (nav rail + grid + detail pane).

Tablet and desktop share the grid + detail-pane core; desktop adds the nav rail. So there is effectively **one wide layout with an optional rail**, not two separate builds - keeps the surface small.

### 4.2 Desktop three-pane (`>=1200`)

```
[ rail 56 ] [ room grid (flex, the star) ] [ Now Playing pane ~336 ]
```

- **Nav rail**: Home (active) + Settings; a theme/accent affordance at the foot. Slim, icon-only. Windows-desktop convention.
- **Grid pane**: the existing Home content (`_HomeContent` body: header, Cards/Stack, group/solo composition) - unchanged logic, just given more width so Cards packs 3-up. Scrolls independently.
- **Now Playing pane**: the dissolved bottom strip, persistent. Shows the **selected** source (or the active source when nothing is selected): album art, title/artist/album, local-tick progress bar, transport, group volume + per-room level sliders, member chips. Empty-selection placeholder when there is no active or selected source.

Room detail, Group editor, and Settings open as **centered dialogs** over this shell (§4.6).

### 4.3 Tablet master-detail (`840-1200`)

Same as desktop minus the rail:

```
[ room grid (flex) ] [ Now Playing detail pane ~320 ]
```

Settings moves from the (absent) rail to a header icon in the grid pane. Below `840` this collapses back to the untouched phone layout, floating strip and all.

### 4.4 Selection model

New `selectedSourceProvider` in `app/lib/src/state/` (a `@riverpod` Notifier holding a nullable group id, `String?` - ids across the state models are plain `String`):

- Default: the first active source in `sourcesProvider`'s deterministic order (that list sorts by label); else `null` (empty pane). The plan's `resolvedSource` implements exactly this via `sourcesProvider.first`, reusing the existing derived active-source list rather than re-deriving a separate ordering.
- Wide: tapping a group card / room card / room row sets the selection; the Now Playing pane rebuilds in place - **no route push**.
- Phone: the existing `Navigator.push` behavior is kept (tapping still opens the pushed Now Playing / Room detail screen).
- The one shared rule: a selected source that disappears (regroup, speaker offline) falls back to the default (first-active-or-null), so the pane never dangles on a dead id. Reuses the same "stale id" discipline the reducer already applies.

The compact-vs-wide fork (push a route vs set selection) lives in the tap handlers, keyed on the same breakpoint helper (§4.6), so the leaf widgets (`GroupCard`, `RoomCard`, `RoomRow`) get one callback that does the right thing per width.

### 4.5 Detail-screen refactor

Today `NowPlayingScreen`, `RoomDetailScreen`, `GroupEditorScreen`, `SettingsScreen` each own an `OtoScaffold` (or `Scaffold`) plus a `Navigator.maybePop` back button - they only compose as full-screen routes. Split each:

- `XxxBody` - the content, chrome-free, no back button, no scaffold. Embeddable in a pane or a dialog.
- `XxxScreen` - the phone route wrapper: scaffold + app bar / back button hosting `XxxBody`.

The wide shell hosts the `*Body` (Now Playing in the pane; Settings / Group editor in a dialog). Phone routes keep the `*Screen`. `RoomDetailScreen` keeps its `*Screen` for phone; on wide it is not composed at all (folded away, §3).

### 4.6 Dialog-vs-route helper

One small responsive helper (e.g. `openSettings(context)`, `openGroupEditor(context, hostId)`), that:

- on wide (`>=840`) shows the `*Body` in a centered `Dialog` (constrained max width/height), and
- on phone pushes the `*Screen` route as today.

Keyed on a single `context.isWide` / breakpoint extension so the branch is defined once. Settings and Group editor route through it. This is the only place the app decides dialog vs route.

### 4.7 Window-size persistence (Windows)

Add `window_manager` (`app/pubspec.yaml`). On desktop startup, restore the last window size + position; on resize/move, persist to `shared_preferences` (already a dependency) under dedicated keys. Best-effort: a missing/invalid saved bound falls back to a sensible default size. No-op on Android (mobile windows are full-screen). Guard all calls behind a desktop-platform check so the mobile build never touches `window_manager`.

## 5. Blast radius

- **Files: `app/lib/src/ui/**` + one new provider in `app/lib/src/state/`.**
  - `ui/shell/oto_scaffold.dart` (wide branch), `ui/shell/oto_app.dart` / `home_page.dart` (host the wide shell), a new nav-rail widget, a new Now-Playing-pane widget (reusing `now_playing` body).
  - `ui/home/home_screen.dart` + tap handlers (`group_card.dart`, `room_card.dart`, `room_row.dart`, `home_header.dart`, `bottom_strip.dart`) route through the selection model / breakpoint helper.
  - `*Body` / `*Screen` splits in `ui/now_playing/`, `ui/room/`, `ui/group/`, `ui/settings/`.
  - New `state/selected_source.dart`; `state/` breakpoint helper.
- **Dart deps:** `window_manager` (new; §7). `shared_preferences`, `flutter_riverpod` already present.
- **Codegen:** riverpod only (`just gen` for the new provider's `.g.dart`). **No FRB regen** - `native/src/api.rs` is untouched.
- **No Rust / cargo / cross-crate work.** None of the §7 backend "ask-first" surfaces (core types, `Wire` trait, FRB surface, `sonos-api` pin) are in play.
- **Showcase:** add a viewport-size toggle (phone/tablet/desktop) parameterizing `_PreviewFrame`; add wide entries. This is where the layout is iterated with hot reload (Task 0, §6).

## 6. Implementation shape (for the task plan)

Spike-first gate, matching the project's habit:

- **Task 0 (spike gate):** showcase viewport toggle (pure infra, decision-independent) + the `OtoScaffold` wide branch + `selectedSourceProvider` + a first-cut three-pane composition, iterated live via hot reload. Fold any proportion/breakpoint findings back into this spec before committing the rest. The spike output is production code (not throwaway) because the showcase renders the real widgets.
- Then: nav rail; Now Playing pane (with per-room levels); dialog-vs-route helper + Settings/Group-editor `*Body` splits; Now Playing / Room detail `*Body` splits + phone-route wiring; `window_manager` persistence; wide integration test.

## 7. Risks, dependencies, prior art

- **`window_manager` dependency (§7 change-control).** User-approved 2026-07-08. It registers a desktop plugin; keep all calls behind a desktop guard so the Android build is unaffected. This is the one new dependency in the milestone.
- **Retired prototype.** `hifi-responsive.jsx` (removed from main in `1f10a77`, still on the `docs/v0.6.1-planning` branch) went list-master-detail with a Queue third pane + search/shuffle/repeat/EQ. It is not backend-true and predates the shipped grid identity, so it is superseded, not followed. The one salvaged, backend-true idea is per-room level sliders in the group's Now Playing detail (§3).
- **Windows becomes first-class.** The `integration_test/` flow on `-d windows` + manual desktop QA carry real weight this release. README already flags that build.yml has no Windows CI job ("Worth revisiting as the v0.6.3 desktop layout makes Windows a first-class target") - decide in the plan whether to add one or keep dev-machine verification.
