# v0.6.2 Settings And States Design

Date: 2026-06-30

## Purpose

v0.6.2 is a UI-side reliability release. It ships a real Settings screen and a
deterministic Home presentation state model for loading, empty, error, cached,
ready, and partial-offline states.

The release does not change backend contracts. It does not add Rust, FRB,
`Wire`, `oto-core`, `sonos-api`, discovery, or live-event surface area. It only
renders existing app knowledge more honestly and consistently.

Primary goals:

- Make first launch, failed discovery, retry, and cached Home behavior clear.
- Replace the Settings stub with useful local preferences and read-only device
  information.
- Keep the implementation backend-true: do not render controls or claims the
  current capability layer cannot support.

Non-goals:

- No manual IP entry, add-speaker flow, network diagnostics, telemetry toggles,
  queue UI, EQ/Sound settings, search, or responsive tablet/desktop shell.
- No new system health engine. The app can present discovery and command-time
  failures, but it cannot detect a whole silent household while idle without a
  backend probe.

## Design Sources

The visual direction comes from `docs/design-system/`, especially:

- `docs/design-system/handoff/HANDOFF.md`
- `docs/design-system/hifi-states.jsx`
- `docs/design-system/hifi-unified.jsx`
- `docs/design-system/handoff/design-tokens.json`

That design system is slightly older than the current Flutter implementation.
For v0.6.2, use it as the source of visual intent and interaction language, but
let current Flutter code define the implemented constraints. When they disagree,
prefer the narrower backend-true interpretation.

Examples:

- Keep the state visual language and spacing from the prototype.
- Do not ship prototype rows for Add a speaker, Network detail, crash reports,
  diagnostics, or audio settings unless a real app capability exists.
- Do not show manual IP entry from the first-run mockup in v0.6.2.

## Home Presentation State

Add a derived UI provider that turns the existing `discoveryProvider` and
`householdProvider` into a small presentation state. The existing providers stay
authoritative. The new provider decides only what Home should render.

Proposed state shape:

```dart
sealed class HomeViewState {
  const HomeViewState();
}

final class InitialLoading extends HomeViewState {}
final class DiscoveringWithCache extends HomeViewState {
  const DiscoveringWithCache(this.household);
  final Household household;
}
final class DiscoveryFailedNoCache extends HomeViewState {
  const DiscoveryFailedNoCache(this.error);
  final Object error;
}
final class DiscoveryFailedWithCache extends HomeViewState {
  const DiscoveryFailedWithCache(this.household, this.error);
  final Household household;
  final Object error;
}
final class Empty extends HomeViewState {}
final class Ready extends HomeViewState {
  const Ready(this.household);
  final Household household;
}
```

`PartialOffline` should not be a top-level state. It is a condition inside
`Ready`: one or more rooms have `online == false`, while the rest of Home remains
usable.

Behavior:

- `InitialLoading`: first discovery is loading and no cached household exists.
  Show a skeleton/loading state.
- `DiscoveringWithCache`: a rediscovery or refresh is loading after a prior
  success. Keep the cached Home visible with a top banner or subtle loading
  affordance.
- `DiscoveryFailedNoCache`: discovery failed before any topology exists. Show a
  blocking error with retry.
- `DiscoveryFailedWithCache`: discovery failed after a prior success. Keep the
  last known Home visible, show a retry banner, and avoid implying more
  certainty than the backend has.
- `Empty`: discovery succeeded but yielded no speakers. Show an empty first-run
  state with retry/scan.
- `Ready`: normal Home.

The state derivation should be pure and unit-tested. It must not mutate
`Household`, change command behavior, or write device/LAN state to disk.

## State Rendering

Use the visual language from `hifi-states.jsx`, narrowed to current capability.

### Loading

Render a Home loading skeleton with scanning copy. The oto mark can be used as
the main visual anchor.

Motion:

- Baseline: use the static oto mark plus existing loading skeleton patterns.
- Stretch: add a subtle pulse or ripple animation to the concentric-square mark
  during first-run/discovery loading only if it stays small.
- Any motion must respect reduced-motion settings. If reduced-motion support is
  not straightforward, defer the animation and keep the static mark.
- Defer native splash-screen customization and richer brand motion to a later
  polish step.

### Empty

Render a centered "No speakers yet" state with:

- Oto/Speakers icon treatment from the design system.
- Short LAN-oriented guidance.
- A primary retry/scan button using provider invalidation.

Do not include Add by IP address in v0.6.2.

### Discovery Error, No Cache

Render a blocking error state with:

- Clear title and concise troubleshooting text.
- Retry button.
- Copy that stays local-first: same Wi-Fi/LAN, multicast/SSDP, no cloud account.

### Discovery Error, With Cache

Keep cached Home visible and add a banner near the top:

- State that refresh/discovery failed and the app is showing cached state.
- Offer retry.
- Do not claim exact "last seen" timing unless the app records that timestamp.
- Avoid disabling the entire Home unless the current data is known unusable.

### Partial Offline

Inline offline rendering stays inside Home cards/rows:

- Dim offline room rows/cards consistently.
- Mark them offline with concise text.
- Gate transport/resume/volume controls for offline rooms.
- Keep online rooms and groups usable.

Existing `RoomState.online` is the source of truth.

### All Quiet

All rooms idle is not an empty or error state. Render normal Home without the
bottom strip.

## Settings

Replace `app/lib/src/ui/settings/settings_stub.dart` with a real Settings screen
reached from the Home header gear.

Keep navigation simple: a pushed `SettingsScreen` route, no routing package.

Sections:

### Appearance

Backed by the existing `settingsProvider`:

- Theme: System, Light, Dark.
- Accent: Teal, Indigo, Amber, Slate.
- Default Home layout: Cards, Stack.

Use inline controls first. Add sub-screens only if the screen becomes cramped in
implementation.

### Devices

Read-only list derived from `householdProvider`:

- Room name.
- Model when known.
- Room kind icon.
- Online/offline state.
- Current group label, or "Standalone" for a one-room group.

No add speaker, manual IP entry, network diagnostics, or device-management
commands.

### About

Include:

- App name and version.
- Local-first copy: controls the user's own Sonos devices on the LAN.
- "Not affiliated with Sonos" copy.

Version source:

- Use a small app constant for v0.6.2 if no existing runtime package-info path
  exists.
- Do not add a new dependency only for build metadata in v0.6.2.
- Keep `app/pubspec.yaml version:` canonical for release updates.

## Components

Add focused Settings UI widgets under `app/lib/src/ui/settings/`:

- `SettingsScreen`
- `SettingsSection`
- `SettingsRow`
- `SettingsSegmentedControl`
- `AccentPicker`
- `DeviceList`
- `DeviceRow`

Use existing app primitives and tokens:

- `OtoScaffold`
- `OtoIcon`
- `OtoMark` where useful
- `context.oto`
- `TextStyles`, `Space`, `Radius_`, `Elevation`

Do not add a new design-system abstraction layer.

For Home states, add focused widgets under Home or shared UI only as needed, for
example:

- `HomeLoadingState`
- `HomeEmptyState`
- `HomeErrorState`
- `HomeStatusBanner`

Keep them small and tied to the current screens.

## Error Handling And Retry

- Discovery retry uses existing provider invalidation/refresh.
- Topology refresh failure behavior stays with the current topology controller
  path. The UI state layer only reflects `discoveryProvider`.
- Command errors stay in `commands.dart`. v0.6.2 keeps silent rollback unless a
  failing control can show a small local affordance without adding a broad
  snackbar/event bus.
- Rollback behavior remains the honest fallback for failed optimistic commands.

## Architecture And Boundaries

Touched layers:

- Flutter state derivation.
- Flutter Home rendering.
- Flutter Settings UI.
- Flutter tests.

Out of bounds:

- `native/` Rust crates.
- `native/src/api.rs`.
- Generated FRB files.
- `oto-core` types.
- `Wire` trait.
- `sonos-api` dependency pin.
- New dependencies unless explicitly approved.

The design preserves the local-first architecture and does not persist Sonos
topology, room, or live state. Only UI preferences remain persisted.

## Testing

Required test coverage:

- Pure provider tests for `HomeViewState` derivation:
  - initial loading with no cache
  - loading with cache
  - failed discovery with no cache
  - failed discovery with cache
  - empty topology
  - ready topology
  - ready topology with partial offline rooms
- Widget tests for Home:
  - loading skeleton
  - empty state
  - no-cache error state
  - cached-error banner
  - ready Home
  - offline room presentation
- Widget tests for Settings:
  - gear opens Settings
  - theme/layout/accent controls update `settingsProvider`
  - Devices list renders known rooms and offline state
  - About renders app identity/version text

Validation gates after implementation:

- `just gen` if Riverpod providers are added or changed.
- `just check`.
- `flutter test` or the Flutter portion of `just test`.

## Implementation Slices

Recommended PR order:

1. Home view-state provider and Home rendering states.
2. Real Settings screen and Devices/About sections.
3. Offline/error polish, loading mark stretch animation if still small, and test
   coverage cleanup.

Keep each slice independently runnable and avoid pulling responsive layout work
into v0.6.2.

## Implementation Defaults

- The oto mark pulse is stretch scope. Ship static loading states first.
- Display app version from a small app constant if runtime metadata is not
  already available.
- Keep command failure feedback as silent rollback unless a small local
  affordance falls naturally out of the touched control.
