# v0.4 — FRB Stream surface pre-check findings

Status: pre-check complete. Companion to [`2026-05-21-v0.4-live-property-events-design.md`](2026-05-21-v0.4-live-property-events-design.md) — resolves § 3.2.

The pre-check exists because v0.4 commits to **one multiplexed `Stream<ChangeEvent>`** through FRB v2 (design constraint § 5.2). The remaining uncertainty before writing `StateManager` was whether FRB's stream surface behaves the way the spec assumes — threading, cancellation, errors, multi-consumer, hot reload. This note records what we observed.

## Verification setup

Three DEV-ONLY Rust functions in `native/src/api.rs`, exercised by `app/integration_test/frb_stream_precheck_test.dart`. Run on Windows desktop via `flutter test integration_test/frb_stream_precheck_test.dart -d windows`. All three tests pass. The dev functions are tagged `TODO(v0.4)` and will be removed when `subscribe_change_events` lands.

| Dev fn | Purpose |
|---|---|
| `dev_tick_stream(sink, interval_ms, count)` | Basic emission + cancel-detection probe |
| `dev_error_stream(sink)` | Error-propagation probe |
| `dev_cancel_observations_count() -> u32` | Read static counter — how Rust signals back to Dart that cancellation was observed |

## Findings

### 1. Basic emission works as advertised

`Stream<T>` from Rust to Dart: `sink.add(value).is_ok()` emits a value; function returning normally completes the stream cleanly. Verified: 5 ticks at 50 ms intervals → Dart received `[0, 1, 2, 3, 4]` in order, stream's `onDone` fired.

### 2. Threading: Rust runs on the FRB worker pool, not the UI isolate

The Rust function body executes on FRB's worker executor (not the UI isolate). **Sync `std::thread::sleep(...)` inside the stream function is fine** — it blocks the worker, not the UI. No special async runtime needed inside the function.

Implication for v0.4: the event-pump thread design ("one OS thread that blocks on `manager.iter()` and pushes to FRB stream") is exactly the shape FRB wants. The stream function blocks on the upstream iterator without async/await, calls `sink.add(event)` per emission, returns when the iterator drops.

### 3. Cancellation is observable — `sink.add` returns `Err` after Dart cancel

When the Dart subscriber calls `subscription.cancel()`, the next `sink.add(...)` from Rust returns `Err`. The Rust side can detect this **without polling** and clean up — observed: `DEV_CANCEL_OBSERVATIONS` counter incremented after a `subscription.cancel()` followed by the next tick.

Implication for v0.4: the event-pump thread checks `sink.add(...).is_err()` after each emission; on error, it can break out and run cleanup (drop subscriptions). No separate cancel channel needed.

### 4. Errors: `sink.add_error(value)` is the channel, **not** `Result::Err` returns

**Most important finding.** Initial assumption (returning `Result<(), String>::Err(...)` from the stream function would surface as `Stream.onError`) is **wrong**:

- Returning `Err` from a stream function: the generated Dart binding wraps the function call in `unawaited(...)`. The `Err` is decoded via the codec but **silently dropped** — it becomes an unhandled async exception, not a Stream error. `Stream.forEach(...)` completes "successfully" with whatever values were emitted before the Err.
- The correct in-band channel is `sink.add_error::<TR: SseEncode>(value)`. Calling that → `Stream.onError(value)` fires on the Dart side, exactly as expected.

Concrete fix to the dev function (also the pattern v0.4 should use):

```rust
// Wrong: error silently dropped.
pub fn dev_error_stream(sink: StreamSink<u64>) -> Result<(), String> {
    sink.add(0).ok();
    Err("...".to_string())  // <-- unawaited; never reaches Dart Stream.onError
}

// Right: error reaches Stream.onError.
pub fn dev_error_stream(sink: StreamSink<u64>) {
    sink.add(0).ok();
    sink.add_error("...".to_string()).ok();
}
```

**Implication for v0.4**: the stream function signature is `pub fn subscribe_change_events(sink: StreamSink<ChangeEvent>)` (no `Result` return). Setup errors (e.g. wire not initialised) belong before the stream is established — they get surfaced as a separate `Future<()>` or as a panic-on-misuse contract, not through the stream. **Runtime errors** that flow alongside `ChangeEvent`s (e.g. "subscription dropped on speaker X") should either:

- (a) Be **typed as a `ChangeEvent` variant** (e.g. `ChangeEvent::SubscriptionLost { speaker_id }`) and emitted via `sink.add(...)` like any other event. UI handles them as data, not exceptions.
- (b) Be **emitted via `sink.add_error(...)`** to terminate the stream with an error.

(a) is more flexible — the stream stays alive, the UI shows the broken speaker state, and recovery can be in-band. **Recommendation: ChangeEvent enum gets `SubscriptionError { ... }` and `SubscriptionRecovered { ... }` variants.** Reserve `sink.add_error(...)` for truly fatal "this stream is dead" situations (e.g. unrecoverable upstream init failure).

### 5. Multiple consumers — not multiplexed via FRB

Each FRB stream-function call creates its own `RustStreamSink`. Two Dart calls to `subscribe_change_events()` → two independent streams → the Rust function runs twice (potentially in parallel on different worker threads). FRB does **not** broadcast one Rust stream to multiple Dart subscribers.

Implication for v0.4: the spec already commits to **one** FRB call per app instance, with Dart-side fanout via Riverpod `StreamProvider`s (filtered per `SpeakerId`). Don't call `subscribe_change_events()` from multiple Dart providers — the broadcasting/filtering happens on the Dart side. This was the spec's plan; just confirming it's the right plan.

### 6. Hot reload — not tested in this pre-check

`flutter test integration_test/...` doesn't exercise hot reload. To verify, run `flutter run -d windows`, trigger a hot reload while the stream is active, observe what happens. Deferred to v0.4 implementation when there's a real UI consumer to test against.

Working hypothesis: hot reload reconstructs the Dart side (new Stream subscription) but the Rust binary stays loaded (FRB cdylib survives). The old stream's `sink.add` will start returning Err (Dart subscriber gone); the new subscription triggers a new `subscribe_change_events` call → new sink, new stream function instance. The event-pump thread for the old subscription should exit cleanly via finding #3.

## Doc updates from this pre-check

- `docs/superpowers/specs/2026-05-21-v0.4-live-property-events-design.md`:
  - § 5.1 (`ChangeEvent` extensibility): add explicit `SubscriptionError` / `SubscriptionRecovered` variants to the enum sketch. Reserve `sink.add_error` for fatal stream termination.
  - § 4 architecture: note that FRB streams don't multi-cast — Dart-side fanout via Riverpod is the documented plan.
- Spike binaries (`dev_tick_stream`, `dev_error_stream`, `dev_cancel_observations_count`): remain on this branch + main until the v0.4 implementation lands. Removed via the v0.4 implementation PR's first commit.

## Out of scope for this pre-check

- Hot reload behaviour (finding #6).
- Memory / leak behaviour of long-lived streams. v0.4 acceptance § 8.7 (30 min `event-tail.rs` runs) covers this on the Sonos data, not synthetic ticks.
- Backpressure under high event volume. Sonos's actual event rates are bounded; the spike (Path A idle = ~30 events/min from real Sonos, peak ~0.5/sec during music) is well within any reasonable FRB throughput. Revisit only if observed.
