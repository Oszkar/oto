# v0.4 — Live property events: design

Status: design (pre-implementation). Sibling docs: [ROADMAP.md](../../ROADMAP.md#v04--live-property-events) (milestone position), [ARCHITECTURE.md](../../ARCHITECTURE.md) (system structure), [sonos-notes.md § Event model](../../sonos-notes.md#event-model-v04-load-bearing) (protocol detail).

## 1. Summary

v0.4 ships **live property events** — volume, mute, transport state, current track — via GENA NOTIFY. Rust subscribes; Dart consumes a single multiplexed `Stream<ChangeEvent>` through FRB. `speaker_state` reads from an event-fed cache instead of issuing SOAP per call. The `Wire` trait's existing signatures are unchanged across the swap (designed in v0.2 for this).

Topology change events, group form/break commands, Android `MulticastLock`, and `model` repopulate are all explicitly **v0.5** and out of scope here.

## 2. Scope

### In

- `StateManager` in `oto-app` caching per-speaker `(volume, muted)` + per-group `(transport_state, track)`. **Watched properties:** Volume, Mute, PlaybackState (transport), CurrentTrack. **Not watched:** `Position` — per spike finding, position is ~95% of all events when subscribed and the cadence is polling-derived. Derive locally for the UI as `(last-known position from a transport event) + (wall-clock elapsed since)`; resync on the next transport NOTIFY.
- One multiplexed event-pump thread inside `oto-wire` (not per-speaker, per the [event-model design note](../../sonos-notes.md#opt-in-via-watch--one-multiplexed-pump-thread)). Feeds an unbounded `std::sync::mpsc::Sender<ChangeEvent>`; the matching `Receiver` is consumed by the FRB worker thread.
- Riverpod `FutureProvider` → `StreamProvider` migration for speaker state.
- `Wire::speaker_state` impl swap: production `oto_app::speaker_state` reads `StateManager` directly (does **not** dispatch through `Wire::speaker_state`); the trait method remains for the v0.3 contract + mock-based tests. Trait signature unchanged.
- The v0.2 ADR carryover is **resolved**: transport moves to **per-group addressing at the event surface** (`ChangeEvent::Playback { group, … }` / `Track { group, … }`), but `SpeakerState`'s external shape stays unchanged — `speaker_state(speaker_id)` resolves transport via the `speaker → coordinator → group` path, honoring the v0.2 "Wire signature stable across the swap" commitment.
- Single FRB `Stream<ChangeEvent>` surface (new FRB function). One call per app instance; Dart-side fanout via Riverpod `StreamProvider`s.
- **Subscribe scope:** `subscribe_speakers()` registers all currently-known speakers from the latest `discover()` snapshot. Invoked automatically by `oto-app::discover()` before returning. Lazy / per-speaker activation deferred to v0.5+ if dogfooding shows event traffic matters.
- `native/examples/event-tail.rs` — Rust dogfooding binary that subscribes and prints events to stdout.

### Out (deferred to v0.5)

- Topology change events (live `ZoneGroupTopology` subscription). `discover()` remains the only topology source through v0.4; stale `GroupId` still returns `WireError::NotFound`.
- Group form/break commands (same SOAP surface as topology events).
- Cache-miss → re-fetch-once self-heal (subsumed by v0.5 topology events).
- Android `MulticastLock`.
- Speaker `model` string repopulate.

### 3.1 Hardware spike — event source + cold-start (one session, two outputs)

Run against the 4-speaker LAN. Produces **two coupled decisions**:

1. **Event source.** Upstream reactive layer (`sonos-state` / `sonos-stream` / `sonos-event-manager`) vs. raw `callback-server` + own change-detection. v0.4 implements **only the chosen path** — do not carry both adapters. The non-chosen path stays a v0.5 reconsideration point if topology events surface new evidence.
2. **Cold-start pattern.** Pick one:
   - `.watch()` as the seed probe (no prior fetch). UI shows "loading" until first event per property.
   - Hybrid fetch + watch, accepting the documented suppression (first change after fetch is silently dropped).
   - Watch + bounded-timeout fetch fallback if no event arrives within N seconds.

These are coupled: if raw `callback-server` wins, the suppression problem changes shape entirely. Deciding sequentially is more expensive than deciding together in the same hardware session.

Spike output is a short findings note that folds into `docs/sonos-notes.md § Event model` at the end of the spike — replacing the current "main thing to settle this milestone" line with the chosen pattern.

### 3.2 FRB Stream surface pre-check

Runs in parallel with 3.1. Not a hardware spike — a verify-before-committing exercise. Confirm Rust `Stream<T>` round-trips through FRB v2 as expected: threading model (does the stream pump from the worker isolate executor?), error propagation, drop/cancel semantics. ~1 hour, scaffold a hello-world `tick_every_second` stream and watch it from Dart. The risk is low (FRB v2 supports streams) but surprises here are much cheaper to hit before `StateManager` exists.

### Concrete shapes

```rust
// oto-core::events
pub enum ChangeEvent {
    Volume   { speaker: SpeakerId, volume: Volume },
    Mute     { speaker: SpeakerId, muted: bool },
    Playback { group:   GroupId,   state: TransportState },
    Track    { group:   GroupId,   track: Track },
    SubscriptionError     { speaker: SpeakerId, message: String },
    SubscriptionRecovered { speaker: SpeakerId },
    // v0.5: TopologyChanged { snapshot: DiscoverySnapshot },
}
```

```rust
// oto-core::wire — additions; existing methods unchanged
pub trait Wire {
    // ... discover + 6 playback methods + speaker_state (signature stable) ...

    /// Register v0.4 property-event interest for all currently-known
    /// speakers (per the latest discover()). Activates the upstream
    /// subscription + the wire's pump thread. One-shot per wire.
    fn subscribe_speakers(&self) -> Result<(), WireError>;

    /// Take the unified event-stream receiver. Returns None if it has
    /// already been taken, or if no subscribe_* call has been made.
    fn take_event_stream(&self) -> Option<std::sync::mpsc::Receiver<ChangeEvent>>;

    // v0.5 (purely additive on this trait):
    // fn subscribe_topology(&self) -> Result<(), WireError>;
}
```

New `WireError` variants: `NoSpeakersDiscovered`, `AlreadySubscribed`. Runtime per-speaker subscription failures surface in-band as `ChangeEvent::SubscriptionError`/`Recovered`, not via this `Result`.

```rust
// oto-app::state — skeleton
pub struct StateManager {
    speakers: RwLock<HashMap<SpeakerId, SpeakerCache>>,
    groups:   RwLock<HashMap<GroupId,   GroupCache>>,
}

struct SpeakerCache { volume: Option<Volume>, muted: Option<bool> }
struct GroupCache   { transport: Option<TransportState>, track: Option<Track> }

impl StateManager {
    pub fn apply_event(&self, event: &ChangeEvent);                  // dispatch on variant
    pub fn speaker_state(&self, id: &SpeakerId) -> SpeakerState;     // speaker→coordinator→group resolution
}
```

Threading: one `oto-wire`-owned OS thread maps upstream `watch_property_with_subscription::<P>` events → `ChangeEvent` → unbounded `mpsc::Sender`. The matching `Receiver`, handed out via `wire.take_event_stream()`, is consumed inside `api.rs::subscribe_change_events`'s loop running on the FRB worker thread: `recv() → oto_app::apply_event(&e) → sink.add(e)`. Loop exits when `recv()` fails (wire dropped) or `sink.add` fails (Dart cancelled — per FRB pre-check § 3). Cache writes happen on the FRB worker; the pump thread doesn't touch `StateManager`'s locks.

`speaker_state(speaker_id)` returns honest partial — `Option::None` for fields not yet seen during the cold-start window (`position_secs: None` always; UI derives position).

Per-crate deltas:

- **`oto-core`** — `ChangeEvent` enum (shape above); `Wire::subscribe_speakers` + `take_event_stream` added; new `WireError` variants `NoSpeakersDiscovered`, `AlreadySubscribed`. No new third-party deps — channel uses `std::sync::mpsc`.
- **`oto-wire`** — owns one dedicated OS thread (the pump). Per-speaker watches via upstream `manager.watch_property_with_subscription::<P>(&sid)`; AVTransport NOTIFYs filtered to coordinator-only via the `speaker_to_coordinator` cache built by `discover()`, then re-emitted with `GroupId` addressing; in-band `ChangeEvent::SubscriptionError`/`Recovered` on observable upstream failures. Pump thread joins on wire drop (upstream manager drops → watches exit). No `Position` watch.
- **`oto-app`** — `StateManager` with per-speaker `(volume, muted)` + per-group `(transport, track)` caches. `apply_event(&ChangeEvent)` mutates the cache. Production `speaker_state(speaker_id)` reads `StateManager` directly (transport resolved via speaker→coordinator→group). `discover()` auto-invokes `wire.subscribe_speakers()` before returning. `Wire::speaker_state` stays on the trait but is no longer dispatched by production code.
- **`oto-mock`** — `subscribe_speakers()` emits seed events per watched property per known speaker (mirrors real cold-start NOTIFY). Mutating methods (`set_volume`, `set_mute`, `play`, `pause`, `next`, `previous`) auto-emit corresponding `ChangeEvent`s. `MockWire::push_event(event)` for adversarial tests (`SubscriptionError`, recovery, timing, out-of-order). `state_of(&speaker_id)` stays for assertions.
- **`native/src/api.rs`** — one new FRB function `subscribe_change_events(sink: StreamSink<ChangeEventDto>)`. Body runs on the FRB worker thread; runs the consumer loop until cancel or wire-drop. Cancel detection via `sink.add(...).is_err()` per [FRB pre-check § 3](2026-05-22-v0.4-frb-precheck-findings.md#3-cancellation-is-observable--sinkadd-returns-err-after-dart-cancel). The three DEV-ONLY pre-check fns (`dev_tick_stream`, `dev_error_stream`, `dev_cancel_observations_count`) are deleted in the implementation PR's first commit. Existing 7 commands unchanged.
- **`app/lib/src/state/`** — `subscribeChangeEventsProvider` (StreamProvider) calls `subscribe_change_events` exactly once and depends on `discoveryProvider` so it auto-rebuilds when discover() replaces the wire. Per-speaker / per-group projections fan out from this stream on the Dart side (FRB doesn't multi-cast — pre-check § 5). `speakerStateProvider` becomes a StreamProvider that filters/projects from the unified stream.

## 5. Design constraints (for v0.5 readiness)

The new v0.5 (topology events + group form/break + hardening) is mostly additive over v0.4 — but only if v0.4 respects four constraints. These are not optional.

1. **`ChangeEvent` is an extensible enum from day 1, including in-band error variants.** Locked shape — see § 4 "Concrete shapes": flat per-property variants (`Volume`, `Mute`, `Playback`, `Track`) + `SubscriptionError` + `SubscriptionRecovered`; v0.5 adds `TopologyChanged` purely additively. Mixed addressing (per-speaker for Volume/Mute, per-group for Playback/Track) reflects Sonos protocol reality. Per the FRB pre-check ([findings § 4](2026-05-22-v0.4-frb-precheck-findings.md#4-errors-sinkadd_errorvalue-is-the-channel-not-resulterr-returns)), in-band errors travel as `ChangeEvent` variants via `sink.add(...)`, **not** as Dart `Stream.onError` (reserve `sink.add_error(...)` for fatal stream termination only).

2. **One multiplexed FRB stream, not one per subscription kind, with Dart-side fanout.** Matches the "one event pump thread" design. v0.5 topology events flow into the same FRB stream — no new FRB surface required. Per the FRB pre-check ([findings § 5](2026-05-22-v0.4-frb-precheck-findings.md#5-multiple-consumers--not-multiplexed-via-frb)), FRB does NOT broadcast one Rust stream to multiple Dart subscribers — call `subscribe_change_events()` exactly once and fan out to per-speaker Riverpod `StreamProvider`s on the Dart side.

3. **`Wire` trait: per-kind subscription methods, unified event delivery.** Locked (see § 4): `fn subscribe_speakers() -> Result<(), WireError>` registers interest; `fn take_event_stream() -> Option<Receiver<ChangeEvent>>` extracts the one unified channel receiver. v0.5 adds `fn subscribe_topology() -> Result<(), WireError>` purely additively — its events flow into the same channel; the receiver is unchanged.

4. **Lock-granularity audit at v0.4 end.** `oto-app`'s doc-comment already flags this: "Revisit if v0.4 event threads contend on the slot lock." If v0.4 introduces a per-device sub-lock, a command channel, or splits the slot lock, document the new shape in the same module-level comment so v0.5 cannot accidentally regress it.

## 6. Cold-start handling

**Resolved by the v0.4 spike (Probe 1, watch-only):**

```rust
let v0: Option<Volume> =
    manager.watch_property_with_subscription::<Volume>(&speaker_id)?;
// v0 is None at this instant — the cache is empty.
// Within ~50 ms (after firewall detection completes), the SUBSCRIBE's
// initial NOTIFY arrives carrying current state for every evented
// variable on the service. The cache transitions None → populated
// automatically. The next `manager.get_property::<Volume>(&speaker_id)`
// returns Some(current_value).
```

The natural "fetch initial state, then subscribe" pattern would silently miss the first event due to documented upstream suppression. We don't use that pattern. **The SUBSCRIBE's initial NOTIFY is the seed probe**, so no separate `.fetch()` step is needed. Probes 2 and 3 from the original spike scope (hybrid fetch+watch, watch + bounded-fetch fallback) are moot.

Detail in [sonos-notes.md § Cold-start: the initial SUBSCRIBE NOTIFY *is* the seed probe](../../sonos-notes.md#cold-start-the-initial-subscribe-notify-is-the-seed-probe).

## 7. Threading and locking

Existing locks (unchanged):

- `SLOT: Mutex<Option<HeldWire>>` — held across each command's blocking SOAP round-trip.
- `DISCOVER_LOCK: Mutex<()>` — held across the full `discover_with` call (make + discover + slot replacement).

New: event-pump thread inside `oto-wire`. Single OS thread, long-lived, multiplexes the upstream `watch_property_with_subscription::<P>` iterators for all `(speaker × property)` pairs. Maps each upstream event to `ChangeEvent` and pushes to an unbounded `std::sync::mpsc::Sender<ChangeEvent>` it owns. Does **not** take `SLOT`. The matching `Receiver`, handed out once via `wire.take_event_stream()`, is consumed by the loop inside `api.rs::subscribe_change_events` running on the FRB worker thread; that loop applies each event to `StateManager` via `oto_app::apply_event` (short write hold on the per-cache `RwLock`) and forwards to the FRB `StreamSink`. Cancel detection via `sink.add(...).is_err()` (FRB pre-check § 3); the consumer loop exits on either Sender-drop (wire replaced) or Sink-error (Dart cancelled).

Interaction points settled, plus what to verify under load:

- A command (e.g. `set_volume(50)`) succeeds via SOAP; the resulting NOTIFY arrives N ms later and is applied to the cache via the consumer loop on the FRB worker. The window between SOAP-success and event-arrival is the consistency window — the v0.6 UI may need optimistic local rendering, but v0.4 does not.
- `discover()` replaces the held wire. Old wire drops → old Sender drops → consumer loop sees `recv() == Err` and returns cleanly; FRB stream completes (`onDone` fires on the Dart side); the Dart `subscribeChangeEventsProvider` (depending on `discoveryProvider`) auto-rebuilds and re-calls `subscribe_change_events` against the new wire's receiver. No mid-stream re-acquire on the Rust side.
- Rapid command bursts during heavy event traffic must not deadlock. Verify under load on hardware (acceptance § 8.12).
- **Lock-granularity audit (v0.5-readiness constraint § 5.4):** the consumer loop on the FRB worker takes the `StateManager` `RwLock`s for each `apply_event` (short write hold); commands still hold `SLOT` across SOAP round-trips. Document any v0.4 sub-lock additions in `oto-app`'s module-level comment before release.

## 8. Hardware acceptance — v0.4 release gate

Run against the 4-speaker LAN. Capture artifacts as PR / release-notes evidence.

**Core event path** (target: sub-second; spike measured operator-action → event arrival in tens of ms on a healthy LAN):

1. Volume change in Sonos app → `ChangeEvent` arrives in oto within ≤ 500 ms.
2. Mute toggle → event arrives.
3. Play / pause in Sonos app → transport-state event.
4. Track skip → current-track event with DIDL parsed.
5. Multiple speakers changing simultaneously → all events surface, no drops, no out-of-order weirdness.

**Cold-start:**

6. Fresh `discover()` → subscribe → first event for each property arrives correctly per the chosen pattern. No silent "waiting forever" for properties that don't change.

**Stability (long-running):**

7. `event-tail.rs` ≥ 30 min on an idle LAN — no memory growth, no subscription drops, no spurious events.
8. `event-tail.rs` ≥ 30 min on an active LAN (music playing, manual volume changes).
9. At least one GENA subscription-renewal cycle observed and survived.

**Resilience:**

10. WiFi drop → reconnect: subscriptions either recover or fail-loud. No silent stale state.
11. Topology drift (regroup in Sonos app during session): stale `GroupId` returns `NotFound` per the documented contract; re-`discover()` heals.
12. Rapid commands during heavy event traffic: no deadlock between slot lock and event-pump thread.

**Regression:**

13. All 6 playback commands work end-to-end (`play / pause / next / previous / set_volume / set_mute`).
14. `discover()` returns the full topology.
15. `cargo nextest run -p oto-wire --features live-tests --run-ignored ignored-only` passes.

**Platforms:**

16. Windows debug build.
17. Android debug APK on a connected device. GENA NOTIFY is unicast TCP — should work without `MulticastLock` — but verify explicitly. Failure here would surface late if not checked.

## 13. Alternatives considered

Preserves the rejected options from the v0.4 architecture brainstorm so future revisits (perf optimization, upstream changes, v0.5+ reconsideration) start with the prior context, not from scratch. The chosen path for each decision is captured in the body of this spec; this appendix is the "what we did *not* do" record.

For the Path A vs Path B decision itself, see [`2026-05-22-v0.4-spike-findings.md`](2026-05-22-v0.4-spike-findings.md) — that decision had hardware evidence and lives in the findings doc.

### 13.1 `ChangeEvent` shape — chose flat per-property variants (§ 4)

- **Rejected: nested `SpeakerProperty { speaker, change: PropertyChange }` wrapper.** Tidier in Rust, but Dart consumers pay with nested `switch` per consumer and FRB codegen produces more layers.
- **Rejected: opaque value (e.g. JSON blob).** Abandons type safety for "extensibility"; strictly worse for a typed Rust+Dart pipeline.
- **Revisit trigger:** unlikely at this scale. If FRB codegen weight for flat variants becomes painful (10+ properties), the nested wrapper is a localized change inside `oto-core::events` + the Dart-side fanout.

### 13.2 `Wire` trait — chose split (`subscribe_speakers` + `take_event_stream`) (§ 4)

- **Rejected: combined `subscribe_speakers(&self) -> Result<Receiver<ChangeEvent>, WireError>`.** Simpler v0.4 surface, but v0.5's `subscribe_topology` would either have an inconsistent shape (no Receiver) or force a trait refactor — violating the "purely additive in v0.5" design constraint (§ 5.3).
- **Revisit trigger:** if v0.5 ships `subscribe_topology` and the split has produced no benefit (the second subscribe call never actually shares the channel in practice), the trait can be collapsed in v0.6 or later.

### 13.3 Threading / pump-thread location — chose wire pump + channel + FRB-worker consumer (§ 4, § 7)

- **Rejected: dedicated consumer thread in `oto-app`.** Adds one thread to decouple StateManager update from the FRB worker. No measured benefit; cancel-detection coordination across the extra thread boundary is harder.
- **Rejected: callback into `Wire::subscribe_speakers` (`Box<dyn Fn(ChangeEvent)>`).** Fewer threads but app-logic (cache update + FRB push) runs on wire's pump thread; harder to instrument (drop counts, backpressure observation); lifetime juggling for the callback closure.
- **Revisit trigger:** if event volume on noisy LANs causes the FRB worker to fall behind (visible as `recv()` channel depth growing in dogfooding), a dedicated consumer thread becomes attractive — the channel seam is already there, only the consumer location changes.

### 13.4 `discover()` ↔ active-subscription orchestration — chose terminate-and-rebuild (§ 7)

- **Rejected: keep the FRB stream alive across `discover()`.** `api.rs`'s consumer loop re-acquires the new wire's receiver on `recv() == Err` instead of returning. No Dart-visible seam, but more orchestration in `oto-app` + `api.rs`.
- **Rejected: atomic swap.** `discover()` waits for old pump to fully drain and FRB consumer to observe before installing the new wire. Significant cross-thread synchronization for invisible smoothness.
- **Revisit trigger:** if users perceive the seam (e.g. brief UI flash when re-discovery runs) and complain. The "keep alive" alternative is an oto-app/api.rs-local change; the wire seam doesn't need to move.

### 13.5 `speaker_state` cold-start + position — chose honest-partial + Dart-side position derivation (§ 4, § 7)

- **Rejected: block-with-timeout (e.g. ≤ 500 ms) waiting for cache to populate.** Smoother first-render UX, but introduces a deadline mechanism for what's nominally a cache read; the ~50 ms cold-start window doesn't justify the machinery.
- **Rejected: fall back to SOAP fetch on cache-miss.** Defeats the point of the cache swap; doubles code paths.
- **Rejected for position: Rust-side derivation (`last position + wall-clock elapsed`).** Doesn't actually save the UI work — the live ticking counter is a Dart timer either way. Position lives in Dart UI for v0.4.
- **Revisit trigger:** if a non-Flutter consumer (e.g. CLI) wants a ready-to-render position with no client-side time math, Rust-side derivation is additive on top of the cache.

### 13.6 Subscribe scope — chose all currently-known speakers (§ 2)

- **Rejected: lazy / per-speaker on-demand subscription.** Wire grows `subscribe(speaker_id)` / `unsubscribe(speaker_id)`; Dart drives activation. Saves event bandwidth that's not scarce in a 4-speaker household; adds orchestration to oto-app and cold-start latency every time a new room is viewed.
- **Rejected: subscribe-all + pause toggle.** Subscribe-all default, `pause_subscriptions()` for power-saving. Surface area without a today-use-case.
- **Revisit trigger:** if Android battery profiling or dogfooding shows the ~120 events/min baseline matters (per-watch polling × per-speaker count is the dominant cost, not GENA traffic). Lazy activation is purely additive on the Wire trait.

### 13.7 Transport addressing in events — chose per-group transport (§ 2, § 4)

- **Rejected: uniform per-speaker addressing.** All `ChangeEvent` variants carry `speaker_id`; transport events carry the coordinator's id. Dart does the `speaker → coordinator` join via discovery. Keeps the enum shape uniform but misaligns from Sonos protocol reality, and per-speaker filtering on the Dart side misses follower transport changes unless the consumer cross-references coordinator.
- **Rejected: split `SpeakerState`, add `group_state(group_id)` Wire method.** Maximally clean data model but breaks the v0.2 `Wire` signature-stability contract that v0.4 was designed to preserve.
- **Revisit trigger:** when v0.6 UI starts and the team decides whether `group_state` as a first-class surface (the "split" option) is worth the API break. Per-group events already provide the underlying data, so v0.6 can add a group-addressed read additively.

### 13.8 Group volume — chose per-speaker `Volume` only, defer (§ 2)

- **Rejected: add `GroupVolume` as a 5th watched property.** Coordinator emits group-aggregated `Volume`; new `ChangeEvent::GroupVolume { group, volume }` variant. Speculative until UI exists.
- **Rejected: Rust-side burst coalescing.** Detect simultaneous per-speaker events and synthesize one GroupVolume event. Heuristic; brittle "Xms" tuning; emits both per-speaker *and* synthesized events.
- **Revisit trigger:** if v0.6 UI shows visible flicker during group-volume changes (Riverpod frame-batched re-rendering should handle it). `GroupVolume` watch + variant is purely additive (one new variant, one extra `watch_property_with_subscription` call per group's coordinator).

### 13.9 `MockWire` affordances — chose realistic (auto-emit + seed-on-subscribe + push_event) (§ 4)

- **Rejected: explicit push only.** Every test composes events manually via `push_event`. Cleanest separation but tests for "command → event arrives" become verbose and *don't* exercise the production cold-start seed-NOTIFY path.
- **Rejected: state-driven only, no `push_event`.** Auto-emit on mutation + seed-on-subscribe; no explicit push. Can't simulate `SubscriptionError` / `SubscriptionRecovered` without a real failure path; adversarial coverage is limited.
- **Revisit trigger:** unlikely. Mock realism is upside-only here; "more affordances than strictly needed" is a deliberate test-leverage choice for a hobby project.

### 13.10 Implementation slice ordering — chose vertical-thin end-to-end first

- **Rejected: bottom-up types-first.** Types → Mock → FRB → Dart → Path A → swap → acceptance. Each layer ships in isolation; architecture risk hidden until the Path A slice fails or succeeds.
- **Rejected: Path A first.** Build the production pump thread first, then layer trait + FRB + Dart on top. Worst order — the highest-risk piece depends on the most decided types being stable.
- **Revisit trigger:** if Slice 1 (skeleton) reveals the architecture itself doesn't fit (e.g. FRB stream + channel + StateManager shape has a bug at the seam), reorder to a fix-the-architecture slice before continuing. Slices 3–5 are the irreversible-cost work; Slices 1–2 are recoverable.
