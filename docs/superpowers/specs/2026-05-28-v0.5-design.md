## 3. S1 — Topology events (Option 3)

The substantive design slice.

### 3.1 Decision: Option 3 (notification + authoritative re-pull)

> **v0.5 SCOPING (decided 2026-06-02, S1.3 implementation).** Option 3's `TopologyChanged` *notification* ships in v0.5 as designed. Its `refresh_topology()` *fast-path re-pull* (the SOAP-only update in §§ 3.3–3.4 below) is **deferred to v0.6** as Option D. v0.5 ships **Option A**: on `TopologyChanged`, the Dart `TopologyController` debounces 250 ms then `ref.invalidate(discoveryProvider)` → a full `discover()` rebuilds wire + pump + topology + caches. Reason: the EventPump's coordinator→group routing maps are frozen at subscribe time, so a fast SOAP re-pull that keeps the pump alive would leave transport/track events mis-addressed after a regroup until the next full discover — correctness depends on uncharacterized SDK AVTransport re-routing. A full re-discover is correct by construction (proven cold-start path), and the Dart contract (`TopologyChanged → debounce → re-pull`) is identical, so swapping in the `refresh_topology()` fast-path in v0.6 (when UI makes the ~3-5 s latency user-visible) is a one-function change. The `refresh_topology()` design in §§ 3.2–3.5 below is therefore the **v0.6 target**, not v0.5-as-built; `Wire::refresh_topology()` exists on the trait in v0.5 but is exercised only by the live hardware test. See plan Task 5 banner.

Three shapes were considered during design:

| | Approach | End-state verdict |
|---|---|---|
| Option 1 | `ChangeEvent::Topology { snapshot }` — SDK ZGT payload propagates to UI | Binds to less-tested SDK ZGT layer; risks propagating bad snapshots; duplicates topology parsing |
| Option 2 | Internal-only freshness mechanism (no UI signal) | Forces a v0.6 hole (UI can't know topology changed); needs re-design at UI time |
| **Option 3** | **`TopologyChanged` notification (no payload) + `refresh_topology()` fast-path** | **Chosen.** Authoritative data via v0.3-proven `GetZoneGroupState` SOAP; smallest FRB surface; debounceable; forward-compatible. |

**Option 1 recorded as a post-1.0 polish candidate.** Once SDK ZGT subscription has live production hardware coverage (months of v0.5+v0.6 dogfooding), the payload may be reliable enough to short-circuit the SOAP re-pull. Upgrade path: extend `TopologyChanged` to carry payload without breaking existing Dart consumers (additive variant or optional field).

### 3.2 Wire trait & FRB surface

```rust
pub trait Wire {
    // ... existing v0.4 methods unchanged ...

    // v0.5 — register the topology-event subscription. One-shot per
    // wire, mirrors subscribe_speakers(). Idempotent — returns
    // WireError::AlreadySubscribed if called twice.
    fn subscribe_topology(&self) -> Result<(), WireError>;

    // v0.5 — re-pull topology authoritatively without re-running SSDP.
    // Uses GetZoneGroupState SOAP against any cached IP (same path as
    // discover()'s topology step). Updates wire's interior caches in-
    // place; returns the fresh snapshot.
    //
    // Distinct from discover() (~3-5 s due to SSDP); refresh_topology
    // is topology-only (~10-50 ms on healthy LAN). Called by oto-app in
    // response to a TopologyChanged event, or by tests/CLIs wanting a
    // fast refresh.
    fn refresh_topology(&self) -> Result<DiscoverySnapshot, WireError>;
}
```

**`ChangeEvent` addition (`oto-core`):**

```rust
pub enum ChangeEvent {
    // ... existing v0.4 variants ...

    // v0.5 — emitted by the wire's topology-event pump when SDK delivers
    // a ZGT NOTIFY. No payload — UI is expected to call refreshTopology
    // to get the authoritative snapshot. Consumers debounce a burst.
    TopologyChanged,
}
```

**FRB DTO + command additions:**

```rust
// native/src/map.rs
pub enum ChangeEventDto {
    // ... existing variants ...
    TopologyChanged,
}

// native/src/api.rs — returns the existing discover() DTO (`Topology`),
// not a new type. discover() today is `fn discover() -> Result<Topology, DiscoveryError>`.
pub fn refresh_topology() -> Result<Topology, CommandError> { ... }
```

**`oto-app::discover_with` change:** auto-invokes `wire.subscribe_topology()` alongside the existing `wire.subscribe_speakers()`. Consumers don't drive subscription explicitly.

### 3.3 oto-app cache update path

**Event flow on a topology change:**

1. **Pump thread in `oto-wire`** receives a ZGT NOTIFY from the SDK reactive layer, emits `ChangeEvent::TopologyChanged` on the existing mpsc channel.
2. **FRB consumer loop in `api.rs::subscribe_change_events`** treats `TopologyChanged` as pure pass-through — converts to `ChangeEventDto::TopologyChanged`, pushes to the Dart `StreamSink`. **No cache mutation in the consumer for this variant.**
3. **Dart's `subscribeChangeEventsProvider`** receives the event, debounces (3.4), then calls `refreshTopology()` FRB command.
4. **`oto-app::refresh_topology()`** runs the actual update:
   - Acquires `DISCOVER_LOCK` (the same lock that serializes `discover_with` — prevents racing with concurrent discovery).
   - Calls `wire.refresh_topology()` → SOAP `GetZoneGroupState` against any cached IP → fresh `DiscoverySnapshot`. Wire's interior caches updated in-place.
   - **StateManager generation bump + clear** (same pattern as v0.4 `discover_with`):
     - Bump `AtomicU64` generation
     - Clear group-keyed caches (transport-per-`GroupId`) — coordinators may have changed
     - Per-speaker Volume/Mute caches **survive** — not topology-dependent. (A vanished speaker's entry persists in-memory for the wire's lifetime; cleared only on wire replacement via the existing `discover_with` generation bump. Acceptable: cache is per-process and ephemeral.)
     - Install the new topology map (speaker → group resolution table)
   - Returns the `DiscoverySnapshot` to Dart.
5. **Dart's `discoveryProvider`** receives the new snapshot, invalidates downstream consumers. (UI consumption is v0.6; v0.5 verifies the snapshot is fresh and propagation works.)

**Cache-update correctness invariants (additive to v0.4):**

- **I1.** `refresh_topology()` is atomic w.r.t. event-apply: caches cleared and topology map installed under the lock, so no event applies against half-updated topology.
- **I2.** `speaker_state` for a speaker that just moved groups returns honest-partial: per-speaker Volume/Mute from the surviving cache; per-group transport `None` until the new group's coordinator emits a Playback NOTIFY. Same shape as v0.4 cold-start.
- **I3.** If `refresh_topology()` SOAP fails (all cached IPs unreachable), wire's interior caches and StateManager are left **unchanged**. Returns `WireError::Network`. Worst case: stale-but-known caches until next attempt or full `discover()`.

### 3.4 Debounce, races, SDK quirks

**Debounce strategy (Dart side):** Trailing-edge, **250 ms window.** Burst of `TopologyChanged` (regrouping in Sonos app emits 2+ NOTIFYs as the operation completes) collapses to one `refreshTopology()` call. Latency under user-perception threshold for non-interactive group-list re-render.

**Race scenarios (additive to v0.4):**

| Race | Resolution |
|---|---|
| `TopologyChanged` during in-flight `refresh_topology()` | `DISCOVER_LOCK` serializes; second one runs after first; redundant SOAP. Acceptable. |
| `TopologyChanged` during in-flight `discover()` | `DISCOVER_LOCK` serializes; `discover()` completes (already refreshes topology); debounce timer fires; `refresh_topology()` runs redundantly. Acceptable. |
| Wire replaced with `TopologyChanged` queued | OLD wire's pump terminates on drop (v0.4 mechanism); event in FRB stream queue; Dart calls `refresh_topology()` against NEW wire; NEW topology returned. Correct. |
| Burst of 3+ `TopologyChanged` in <250 ms | Debounce collapses to one `refresh_topology()`. |
| `refresh_topology()` SOAP fails mid-debounce | Error to Dart; caches unchanged; next event or `discover()` re-tries. |
| Pump receives `TopologyChanged` after wire dropped | Stop flag set; pump exits at next poll; sender dropped; FRB consumer's `recv()` returns Err; stream completes. v0.4 mechanism. |

**SDK quirks (informed by P0c findings):**

The spike-findings noted ZGT has less upstream hardware coverage than AVTransport/RC. P0c answers concrete questions:

1. **Per-speaker or per-household subscription?** Design default: subscribe on the coordinator of each group (mirrors AVTransport routing). If P0c shows per-household, simplify. If per-speaker, subscribe each.
2. **NOTIFY reliability on regroup/member-add/member-remove/rename:** P0c probes all four. Silent variants get documented; degraded fallback is the v0.4 stale-`GroupId` → `NotFound` contract.
3. **NOTIFY payload shape:** opaque to S1 (we re-pull via SOAP regardless); captured for the recorded Option-1 follow-up.

**Fallback if P0c shows ZGT NOTIFYs are flaky:** S1 still works — stale `GroupId` → `WireError::NotFound` is the existing v0.4 contract. UI catches NotFound, prompts re-discover. Worse UX, not broken. S2 SubscriptionError sweep catches dead ZGT subscription independently if it goes silent for >2× renewal threshold.

## 4. S2 — SubscriptionError reactive emission

**Background:** v0.4 added `ChangeEvent::SubscriptionError`/`SubscriptionRecovered` to the trait + DTO surface, but production never emits them (SDK at `=0.5.2` swallows per-speaker failures with `tracing::warn!`). v0.5 makes them fire.

**Approach A — reactive emission on command failure.** Three were considered:

| | Approach | LAN cost | Proactiveness | New mechanism |
|---|---|---|---|---|
| **A** | **Reactive — emit on `WireError::Network` command failure** | Zero | Detects on user-initiated commands | None |
| B | Tracing-driven (capture SDK warn events) | Zero | Proactive | Tracing subscriber + SDK log-format coupling |
| C | Heartbeat probe | ~1 SOAP/speaker/5min | Most proactive | New sweeper thread |

**A chosen** because zero new mechanisms, simplest-working contract that satisfies the v0.4 forward-compatibility hook.

### 4.1 Design

**In `oto-app`** (new state — fold into `StateManager` or sibling):
- Per-speaker `enum HealthState { Healthy, Errored }`
- On every **command dispatch** that goes to the wire (`play`, `pause`, `next`, `previous`, `set_volume`, `set_mute`). **Excludes `speaker_state`** — v0.4 swapped that to a cache read; it issues no SOAP and is not a health-check signal.
  - `Ok` and prior state was `Errored` → emit `SubscriptionRecovered { speaker_id }`, set Healthy
  - `Err(WireError::Network(_))` and prior state was `Healthy` → emit `SubscriptionError { speaker_id, reason }`, set Errored
  - `Backend` / `NotFound` errors don't change health state (pre-condition / device-rejection, not connectivity)
- Emission is **transition-edge only** (one event per state change, not per error).
- Events flow on the same FRB stream as v0.4 (mpsc channel; same consumer loop).
- **State resets to Healthy on wire replacement** (`discover_with`) — generation-token-aligned.

### 4.2 Testing

- Unit (oto-app): mock returns Network error → `SubscriptionError` emitted; mock returns Ok → `SubscriptionRecovered`; mock returns Backend → no health change.
- Integration (Dart via MockWire): drive a sequence of command failures + recoveries; assert events arrive in correct order.
- No live hardware test required — failure modes deterministic via mocks; live tests would be brittle (depending on real speaker behavior we can't reliably trigger).

### 4.3 Post-1.0 follow-ups (recorded, not v0.5 work)

Per [[feedback-v1-polish-post-release]]:

- **Approach B (tracing-driven)** — better proactive coverage. Spike feasibility once SDK 0.5.2's tracing format is verified to use structured fields for speaker IDs. Could be a small post-1.0 PR.
- **Approach C (heartbeat probe)** — most proactive. Only worth it if real-world dogfooding surfaces "speaker silent for an hour, I had no idea" complaints. Wait for data.

Both go into ROADMAP "project-bound open items."

## 5. S3 — Android `MulticastLock`

**Background:** Android silently drops SSDP multicast without a held `WifiManager.MulticastLock`. Release builds get no responses (debug works for an unrelated reason — adb keeps the WiFi radio active in non-power-save mode). `AndroidManifest.xml` already declares `INTERNET` + `CHANGE_WIFI_MULTICAST_STATE`. Marked `TODO(v0.5)` since v0.1.

### 5.1 Where the lock lives

**Not in Rust.** JNI from `oto-wire` would couple a "no platform-specific code" crate to Android Java APIs. Wrong layer.

**In Flutter Kotlin via `MethodChannel`.** Kotlin handler in `app/android/app/src/main/kotlin/me/oszkar/oto/MulticastLockHandler.kt`. Dart wraps `discover()` to acquire before and release after.

### 5.2 Lifecycle

Lock held **only during the SSDP M-SEARCH window** (~3-5 s inside `discover()`):
- After SSDP completes (Phase 1 done), rest of discovery is SOAP/HTTP unicast — no lock needed.
- GENA event delivery (v0.4) is unicast TCP — no lock needed.
- `refresh_topology()` from S1 is SOAP-only — no lock needed.

Acquire before, release after. Per-discover granularity (not permanently held).

### 5.3 Dart wrapping shape

```dart
// app/lib/src/state/discovery.dart  (modify existing discoveryProvider)
@Riverpod(keepAlive: true)
class Discovery extends _$Discovery {
  @override
  Future<DiscoverySnapshot> build() async {
    if (Platform.isAndroid) {
      await AndroidMulticastLock.acquire();
      try {
        return await discover();
      } finally {
        await AndroidMulticastLock.release();
      }
    } else {
      return await discover();
    }
  }
}

// app/lib/src/platform/android_multicast_lock.dart  (new)
class AndroidMulticastLock {
  static const _channel = MethodChannel('me.oszkar.oto/multicast_lock');
  static Future<void> acquire() => _channel.invokeMethod('acquire');
  static Future<void> release() => _channel.invokeMethod('release');
}
```

### 5.4 Kotlin side

```kotlin
// app/android/app/src/main/kotlin/me/oszkar/oto/MulticastLockHandler.kt  (new)
class MulticastLockHandler(context: Context) : MethodChannel.MethodCallHandler {
    private val wifiManager = context.applicationContext
        .getSystemService(Context.WIFI_SERVICE) as WifiManager
    private var lock: WifiManager.MulticastLock? = null

    override fun onMethodCall(call: MethodCall, result: MethodChannel.Result) {
        when (call.method) {
            "acquire" -> {
                if (lock == null) {
                    lock = wifiManager.createMulticastLock("oto-ssdp").apply {
                        setReferenceCounted(true)
                    }
                }
                lock?.acquire()
                result.success(null)
            }
            "release" -> {
                lock?.release()
                result.success(null)
            }
            else -> result.notImplemented()
        }
    }
}
// Registered in MainActivity.configureFlutterEngine(...)
```

Reference-counted so overlapping `discover()` calls don't release prematurely. Android cleans up the lock on app death.

## 6. S4 — Model repopulate

**Background:** `ZoneGroupTopology` XML has no model attribute, so `SpeakerIdentity.model` is `None` since v0.3. Fetch via `http://<ip>:1400/xml/device_description.xml`. Per sonos-notes: use `ureq` (handles Sonos's mandatory chunked transfer encoding) + `quick-xml`.

### 6.1 Design

- **Where:** Inside `discover()`, after topology parsing and snapshot construction, before returning. Adds ~50-200 ms (parallel per-member fetches with bounded timeout). Snapshot complete on return.
- **Also in `refresh_topology()`:** consistent semantics across both topology-source operations.
- **Concurrency:** spawn N threads (one per topology member), join all with 2-second deadline. Sequential would balloon worst-case latency to N × timeout.
- **Timeout:** `ureq::Agent` with `timeout_connect(Duration::from_secs(1))` + `timeout(Duration::from_secs(2))`. Fetch failure → `model` stays `None`; discovery does not fail.
- **Parsing:** `<modelName>` element ("Sonos Era 100", "Sonos Beam", etc.). quick-xml event-driven parse.

### 6.2 No caching

Model fetch repeats on every `discover()` / `refresh_topology()`. Cost is low (~100 ms parallel), speakers can come and go from `<VanishedDevices>`. Caching adds invalidation complexity for no real benefit at this scale. Revisit only if discover latency becomes user-visible.

### 6.3 Testing

- Live hardware (gated): asserts model populated for Era 100 + Beam after discover.
- Unit: not directly applicable — model comes from XML fetch; MockWire just sets it.

## 7. S5 — Lock-granularity revisit (conditional)

**Default: SKIP.** v0.4 dogfood showed no contention between event-apply writes and command-time `SLOT` holds.

### 7.1 Measurement during S1/S2 dogfood

Add `tracing::debug` spans around oto-app's slot lock + `DISCOVER_LOCK` during the v0.5 acceptance dogfood (≥30 min idle + ≥30 min active, mirroring v0.4 but with topology events firing). Capture lock-hold-time histograms in `event-tail` logs.

### 7.2 Trigger conditions

S5 fires only if v0.5 dogfood produces:
- p99 command latency >200 ms attributable to lock contention (lock-wait dominating SOAP time)
- p99 event-apply lag >100 ms attributable to consumer-side lock contention
- Any deadlock observed

### 7.3 If triggered

Fix depends on which lock contends:
- **Slot lock (`Mutex<Option<HeldWire>>`):** switch to `RwLock`; commands take read locks for routing decisions, hold a per-speaker fine-grained lock during SOAP. Separate v0.5 follow-up PR.
- **`DISCOVER_LOCK`:** `refresh_topology` calls stacking — reconsider debounce window or add a "refresh already pending" short-circuit on the Dart side.

### 7.4 If not triggered (expected)

Record histograms in v0.5 release-evidence; mark S5 closed-without-change in CHANGELOG.
