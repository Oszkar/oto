# v0.3 grouping — ZoneGroupTopology spike plan

**Date:** 2026-05-19
**Status:** Spike code written; awaiting the real-hardware run.
**Gates:** the v0.3 grouping design (the `Wire`/`oto-core` topology
surface). No product code is committed from the spike — same discipline
as the [discovery spike](2026-05-15-discovery-spike-findings.md) and the
[playback spike](2026-05-18-playback-spike-findings.md).

## Why a spike first

v0.3 is **Grouping** — real ZoneGroupTopology (multi-room groups,
coordinator election, bonded/surround), reads still one-shot (events are
v0.4). The historical risk (ARCHITECTURE **Open Q1**): `sonos-sdk`'s
`SonosSystem::from_discovered_devices` → `speakers()`/`groups()` was
hardware-proven **lazy / non-deterministic** (1 of 4 speakers, flapping
0↔1). v0.1 and v0.2 therefore bypass it — own SSDP for identity, direct
`sonos_api` SOAP for playback. v0.3 needs *real* topology; before we
shape the `Wire`/`oto-core` grouping surface we de-risk the path, exactly
as v0.2 did for playback.

**Hypothesis:** `sonos_api`'s `zone_group_topology::get_zone_group_state`
issued via `SonosClient::execute_enhanced(ip, op)` (no `SonosSystem`, no
`ensure_topology()`) is the deterministic, complete, household-global
(`ServiceScope::PerNetwork`) topology path — the topology analogue of the
v0.2 direct-SOAP playback escape hatch. The crate also ships
`parse_zone_group_state_xml(&str) -> Result<Vec<ZoneGroupInfo>>`
(`coordinator` / `id` / `members` / `satellites`), so — unlike DIDL,
which `sonos_api` did **not** decode — decoding may be free. The spike
proves or breaks this on real hardware.

## Questions the spike must answer (do not guess at design time)

1. **Dispatch / sync.** `get_zone_group_state().build()` +
   `execute_enhanced(ip, op)` → `GetZoneGroupStateResponse {
   zone_group_state: String }` returns `Ok` on real hardware; blocking,
   no tokio (same client as v0.2 — quick confirm).
2. **Determinism + completeness vs. Open Q1.** ×10 against the LAN: the
   **complete** household every call (incl. the bonded SYMFONISK→Beam
   surrounds), stable group/member counts, ≤1 distinct XML variant when
   topology is unchanged — i.e. *not* the SonosSystem flap. Query 2–3
   different speaker IPs; `PerNetwork` ⇒ each must report the same
   household.
3. **Parse strategy (largest unknown — the DIDL-equivalent).** Does
   `parse_zone_group_state_xml` cleanly decode the **control-response**
   string (it lives in the crate's `events` module — confirm it is
   usable off the event path) into correct `ZoneGroupInfo`? If it fails
   or loses data → `oto-wire` parses the XML itself with `quick-xml`
   (already in-tree from v0.2). Record the field → `oto_core` mapping
   either way, for: (a) all-solo, (b) a real ≥2-room group, (c) the
   bonded pair / surround case.
4. **Coordinator + GroupId → `oto_core::Group`.** `ZoneGroup@Coordinator`
   (UUID) and `ZoneGroup@ID` (`RINCON_…:N`, matching discovery-spike
   finding) present; coordinator UUID appears among members (validates
   oto-core **D3** — members include coordinator). Bonded satellites
   surface via `SatelliteInfo` (`invisible`, `ht_sat_chan_map_set`) —
   the answer to the long-deferred bonded question (**Open Q4** /
   oto-core non-goal).
5. **The v0.2 seam generalises (user-gated, mutating — `--play-check`).**
   With a 2-room group formed manually in the Sonos app: resolve its
   coordinator from `get_zone_group_state`, issue v0.2's proven
   `av_transport::play` at the coordinator IP — do **all** rooms start?
   Confirms `GroupId → coordinator → IP → execute_enhanced` works for
   real groups with **zero `Wire` signature change** (the seam the v0.2
   design promised).
6. **One-shot suffices for v0.3.** Re-group in the Sonos app; a fresh
   `get_zone_group_state` reflects it ⇒ re-fetch-on-demand is enough for
   v0.3. Explicitly defers `.watch()` / the watch-after-`fetch()`
   suppression (**Open Q6**) and topology-change *events* to **v0.4**.

## Method

- Throwaway `native/crates/wire/examples/topology_spike.rs`. Read-only
  by default (Q1–Q4, Q6 via re-run); Q5 only under `--play-check` after
  a manual group is formed. Compile-checked in CI/sandbox; **run on the
  real LAN by the user** — SSDP/SOAP cannot run from a sandboxed shell
  (AGENTS.md §5).
- Run:
  ```text
  cargo run -p oto-wire --example topology_spike -- <ip> [<ip> ...]
  cargo run -p oto-wire --example topology_spike -- --play-check <ip>
  ```
  Capture stdout for: all-solo; after forming a 2-room group; with the
  bonded surround present. (Get IPs from the v0.1 discovery path or the
  router DHCP table.)
- Findings → `docs/plans/2026-05-19-v0.3-grouping-spike-findings.md`
  (written from the run output), which then gates the v0.3 grouping
  design — the same flow as the two prior spikes.

## Out of scope (deferred, stated)

- Topology-change **events** / `.watch()` / Open Q6 → **v0.4**.
- Group **form/break commands** (`SetAVTransportURI` / join-leave) →
  v0.3 *implementation*, not this spike (spike is read + one gated
  play cross-check).
- Reshaping `oto_core::Group`/`Speaker`, the `Wire` topology surface →
  the v0.3 design this spike gates.
